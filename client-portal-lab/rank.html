Client Portal Lab · F05 + F06 · rank study

100 reviewers. 10 variants. One ranking.

I role-played 100 distinct users — different jobs, companies, countries, screens, abilities, tastes and goals — and had each one score all 10 hand-authored variants across 10 criteria using their own priorities. Every reviewer produced a full 1–10 ranking; the aggregate is below, together with family ranks, segment winners, a criteria matrix and a head-to-head win matrix.

Honesty first: these are 100 simulated personas, not real people. Scores are a deterministic, seeded model (seed 20261027) built on criterion ratings derived from static code analysis of the 10 files and the documented design facts — not from a browser, screenshots, or real user testing. It is a structured way to expose blind spots and relative strengths, not a substitute for human research. See Method & limits.

Clarity

Information hierarchy, H1 scale, above-the-fold comprehension in <2s, KPI/verdict legibility.

Distinctness

Unique geometry and narrative vs siblings; anti-drift / not an identical skin.

Accessibility

Keyboard paths, ARIA, focus management, reduced motion, AA contrast, skip links, live regions.

Responsive

360/390/768/1024/1440 reflow, mobile card fallback, sticky behaviour, no horizontal scroll.

Performance

Page weight, inline script size, zero external requests, zero image payload.

Interaction

Real working interactions: command palette, sort, stepper, live preview, board nav, dropzone.

State coverage

Populated, empty, loading/skeleton, error+retry, success, cancel-without-losing-work.

Guidance

Help affordances, inline validation, tooltips, budget guide, word count, in-context hints.

Honesty

No invented rows/rates/APIs; demo-labelled CTAs; frozen-content fidelity; audit-truthful copy.

Consistency

One token scheme, light/dark parity, brand discipline, semantic HTML, reduced-motion parity.

Method & limits

reproducible

Everything here is computed by rank/build_rank.py with seed 20261027. Re-running it produces byte-identical results. No variant HTML/CSS was generated or modified by that script.

How the 100 personas were built
  • 20 archetypes × 5 individuals = 100 distinct reviewers. Archetypes range from first-time clients and agency ops leads to screen-reader users, low-vision users, QA engineers, designers, procurement managers and legal/compliance officers.
  • Every individual has a unique name drawn from 7 world regions, an employer type, a device (360 / 390 / 768 / 1024 / 1440 px), an experience level, an accessibility need, an aesthetic taste, a priority and a task goal.
  • Those attributes deterministically produce a 10-dimension weight vector (normalised to sum 10, with seeded ±16%% jitter). Example: a screen-reader user weights accessibility ~3× a baseline user; a 360px mobile user weights responsive ~3.5×; a designer weights distinctness ~3×.
  • Each reviewer scores every variant as weighted criterion mean → quality score (58 + (mean − 80) × 2.0) + taste-fit bonus (0 or +6) + task-relevance bonus (0–5.5, so work-hub users favour F05 and form-fillers favour F06) + device penalty + seeded taste noise (σ=1.6). Scores are clamped to 0–100. Each reviewer then produces a full 1–10 ranking.

Why task-relevance bonus? A real user comparing a request list with a request form is not making a pure craft judgement — they have a job to do. Adding a bounded family bonus makes the simulation realistic and lets us also report a neutral-craft view through the "Evaluate templates" and "Audit accessibility" segments (35 reviewers with no family bias).

How criterion ratings were derived
  • Measured from the 10 files: page weight (42–57 KB), inline aria- attribute counts (48–90), @media breakpoints (3–4), keydown handlers (1–4), reduced-motion rules, and verified structural capability flags (command dialog, aria-sort, density toggle, aria-current="step", IntersectionObserver scroll-spy, roving arrow-key board, count-up, live preview, budget guide, saved views, focus management, live regions, mobile cards, autosave, accordion, help affordances, state panels).
  • From the design docs: the frozen-content fidelity, honesty decisions, distinctness axes, signature interactions, state coverage and family ADDs recorded in CONCEPTS.md and both DELIVERY-REPORT.md files.
  • Shared floor: all 10 variants pass the same baseline — 0 runtime errors, 0 undefined tokens, 0 remote URLs, 0 dead links, light+dark, reduced motion, keyboard, 6 designed states, 32px H1 floor. The criteria matrix differentiates on how far above that floor each variant goes.
Limitations — please read
  • These are not real users. They are simulated personas generated by a rule-based model. No human, no survey, no analytics and no session recordings were involved.
  • No screenshot / pixel / real-browser QA. No Chromium / Chrome / Firefox / Playwright binary exists in this sandbox. Criterion ratings are reasoned from static code + CSS, not from rendered screenshots at 360/390/768/1024/1440 in light and dark. jsdom runtime QA was run on all 10 variants (0 errors), but jsdom does not paint.
  • Criterion ratings contain expert judgement. They are defensible and evidence-linked, but they are not objective measurements. Different baseline ratings would shift the ranking. That is why the full matrix, the weights and the seed are published — so the result is auditable and re-runnable.
  • Cross-family ranking compares craft, not fitness for purpose. Use the per-family leaderboards to choose a template for a real task.
  • Small margins are real. Several variants are separated by <2 points. Treat the top cluster as a shortlist, not a strict order.
